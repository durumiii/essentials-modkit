# modkit — Essentials 모드 표준과 스탠드얼론 매니저 설계

2026-08-03 · 브레인스토밍 확정본. 구현 계획의 입력이 되는 문서다.
최종 거처는 sketches 풀의 새 프로젝트 `modkit`이며, 이 문서는 그 씨앗으로 옮겨 간다.

## 배경과 목표

포켓몬 Z 한글패치 v5 배포 후, 유저들이 옛 패치가 덮인 설치본 위에 새 패치를
얹다가 버그를 만나는 일이 반복되고 있다. fanlib의 모드 매니저(modstore)는 이
문제를 풀 재료 — 모드 카드(mod.json), 세 가지 설치 계약, expects 해시 검증,
베이스라인 — 를 이미 갖추고 있으나 개인 라이브러리 속 부품이라 공유할 수 없다.

목표: 이 코어를 **modkit**이라는 독립 프로젝트로 이사시켜 정본으로 삼고,
Essentials 팬게임 전반에 통하는 모드 단위·관리 규약을 스펙 문서로 확립하고,
일반 유저가 더블클릭으로 쓰는 GUI까지 얹어 공유한다. fanlib은 modkit을
가져다 쓰는 소비자가 된다.

대상 사용자는 둘 다: 패치·모드 제작자(CLI, 카드 규약)와 일반 설치 유저
(exe, 진단·격리·얹기/빼기).

## 1. 아키텍처와 저장소 배치

- **modkit(새 sketch, 정본)**: fanlib에서 모드 코어를 이사시킨다 —
  modstore·modassets·modfit·rubyread·rubywrite가 modkit 소유가 되고 fanlib에는
  남지 않는다. 구성:
  - `modkit/` 패키지 — 코어 5모듈 + 진단(매니페스트) 모듈. 외부 의존은
    rubymarshal 하나. fanlib에 기대던 세 지점(게임 제목 `entry`, 버전 지문
    `fingerprint`, 시각 `launch`)은 인자로 받거나 modkit 안에 최소 구현으로
    풀어 의존 제로로 만든다.
  - `app.py` — 유저용 GUI + 제작자용 CLI 진입점(인자 있으면 CLI, 없으면 GUI).
  - `SPEC.md` — 표준 문서(6절 참고).
  - `build.py` — PyInstaller exe 조립.
- **fanlib(소비자)**: `from modkit import ...`로 갈아탄다. 호출부(install.py·
  pokemonz.py·web.py 등)가 많으므로 과도기엔 fanlib 쪽에 한 줄 재수출 심
  (`fanlib/modstore.py` → `from modkit.modstore import *`)을 둔다. 경로 연결은
  make_package.py의 `FANGAME_LIBRARY` 패턴을 뒤집은 `MODKIT` 경로 임포트
  (sketch 단계). pip 설치형 패키징은 필요해질 때.
- **pokemon-z의 vendor/fanlib(rubyread·rubywrite 사본)**: 이번엔 안 건드린다.
  배포된 번역표와 한 벌이라 그대로 두고, 다음 판 배포 때 modkit 산으로 교체할지
  그때 판단한다.
- **수정 규율**: 모드 코어 수정은 modkit에 먼저. fanlib은 심을 통해 따라온다.

## 2. 모드 카드 v1 — 선언 필드 포함

카드는 기존 mod.json을 표준화한 것. 모드의 정의는 「폴더 하나 + mod.json 한 장 +
사람이 읽을 수 있는 .rb와 에셋 원본」이고, 배포 단위는 이 폴더의 zip이다.

기존 필드(name·game·engine·install·description·scripts·assets·expects·meta·
출처 기록)에 **제작자 선언부**(전부 선택, 권장)를 더한다:

```json
"touches":   { "methods": ["Scene_Map#update", "Window_Base#draw_text"],
               "files": ["Graphics/Pictures/MenuNormal.png"] },
"order":     { "after": ["한글패치 통합"], "before": [] },
"requires":  ["한글패치 통합"],
"conflicts": { "Better Menus": "같은 메뉴 씬을 통째로 갈아 끼움 — 공존 불가" }
```

- **touches는 반자동**: modfit이 베이스라인을 뜰 때 재정의 메서드를 이미
  계산하므로, harvest 시점에 도구가 touches 초안을 채우고 제작자(또는 모드를
  만드는 에이전트)는 확인·보충만 한다. 선언을 공짜로 만들어야 실제로 채워진다.
- **order**: 이름 붙은 모드 상대의 앞/뒤 제약. 묶음형은 배열 위치, 주입형은
  섹션 삽입 위치로 실현된다(마지막 재정의가 이기는 엔진이라 순서가 곧 의미).
- **requires / conflicts**: 의존과 공존 불가를 사유와 함께.

## 3. 설치 계약 3종과 적용 시 검사

계약은 modstore가 이미 지키는 것을 표준으로 승격:

- **묶음형** — PluginScripts.rxdata 끝에 얹기(현대 Essentials).
- **주입형** — Scripts.rxdata의 `MOD:<모드명>/<파일명>` 섹션을 Main 앞에 꽂기
  (묶음 없는 옛 엔진).
- **에셋형** — CRC 대조 기반 파일 교체(`replaces_crc`).

적용 시 검사는 세 겹:

1. **차단**: `requires` 미충족, `conflicts` 해당 → 사유를 보여주고 멈춘다.
2. **자동 배치**: `order` 제약을 만족하는 자리에 끼워 넣는다. 제약이 순환하면
   목록을 보여주고 중단.
3. **경고**: 선언 없는 모드끼리 touches(자동 추출분 포함)가 겹치면 알리되 막지
   않는다 — "둘 다 `Scene_Map#update`를 건드려요. 순서 선언이 없어 나중 것이
   이겨요." 로그에 남긴다.

선언 없는 옛 모드도 지금처럼 동작하고 기계 감지(3)만 받는다.

## 4. 안전 규약

- 첫 쓰기 전 `.orig` 백업, 이미 있으면 덮지 않는다.
- 쓰기 전 왕복 확인(직렬화→역직렬화 대조), 원자적 교체(옆에 쓰고 rename —
  하드링크 함정 회피), CRLF 보존.
- 게임 귀속: 카드의 `game`과 설치본 제목이 다르면 거부(WrongGame).
- 파괴 동사 없음: 삭제 대신 격리(5절).

## 5. 매니페스트와 진단 — 정체불명 설치본 문제

- **매니페스트**: 제작자가 깨끗한 원본에서 `modkit manifest <게임폴더>`로 뽑는
  JSON 한 장 — 게임 이름·버전 라벨·파일별 (상대경로, 크기, CRC32)·제외 규칙
  (세이브·설정·스크린샷 등 유저 데이터). CRC32는 modassets의 `replaces_crc`와
  한 벌이고 수천 파일도 수초. 패치 zip에 동봉하는 것이 제작자 규약.
- **진단 판정 — 파일마다 넷 중 하나**:
  1. 원본 일치. 2. 아는 변경(보관소 카드가 설명 — "UI Text KR이 얹은 파일").
  3. 외래(어떤 카드도 설명 못 하는 변경·추가 — 옛 패치 흔적, 주 타깃).
  4. 누락(설치본 손상). 도구 자신의 백업(`.orig`)은 따로 분류.
- **격리**: 외래 파일은 지우지 않고 게임 폴더 안 `_quarantine/<날짜>/`로
  상대경로 보존 이동. 통째로 되돌릴 수 있다.
- **설치 흐름 결합**: 패치 적용 전에 진단이 먼저 돈다. 깨끗하면 진행, 외래가
  있으면 목록을 보여주고 「격리 후 설치(권장) / 그냥 덮기 / 중단」. 매니페스트가
  없는 패치는 진단 없이 동작(판정 1·4만 빠지고, 카드 기반 판정 2는 가능).

## 6. 유저용 exe와 GUI

- **껍데기**: PyInstaller 단일 exe(윈도우). HTML UI를 **pywebview**(Edge
  WebView2 — Win10/11 기본 내장)의 자기 창에 띄운다. 브라우저 방식의 세 한계
  (폴더 선택 불가, 탭 닫아도 서버 생존, 기본 브라우저 복불복)를 없애기 위한
  선택. 폴더 선택은 네이티브 대화창, 창 닫기=종료. WebView2 없는 드문 환경은
  브라우저 폴백. 개발 중엔 `uv run app.py`.
- **유저 화면 세 걸음**: ① 게임 폴더 지정(최근 폴더 기억) → ② 진단 화면
  (판정 결과를 신호등처럼, 외래 있으면 [격리 후 진행]이 기본) → ③ 모드 서랍
  (설치/보관 목록, [얹기]/[빼기], 모드 zip 끌어놓기 → exe 옆 `mods/` 보관소).
- **제작자 CLI는 같은 exe**: `manifest` · `harvest` · `apply` · `remove` ·
  `diagnose`.
- 진단 결과와 행동 로그를 게임 폴더에 남겨 다음 진단이 이어 읽는다.

## 7. SPEC.md 목차

1. 모드의 정의(폴더+카드, 배포 단위 zip)
2. 카드 형식 v1 — 필드 사전, 필수/선택, 선언 필드, 게임 귀속 원칙
3. 설치 계약 3종 — 얹기·빼기·갈아끼우기 규칙, 적용 시 검사 3겹
4. 안전 규약 — 백업·왕복 확인·원자적 교체·CRLF
5. 매니페스트와 진단 — 형식, 판정 4종, 격리
6. 호환성 검증 — expects md5, 베이스라인, 판 올림 절차

## 8. 검증 계획

- **코어 회귀 테스트**(pytest): 합성 rxdata로 얹기→빼기 왕복 바이트 동일성,
  진단 판정 4종 픽스처, 검사 3겹(차단·배치·경고) 시나리오. 이사 오는 코드가
  실전 검증됐어도 fanlib 의존을 끊는 수술 자체가 회귀 지점이라 필수.
- **실물 검증 둘**: ① 포켓몬 Z(주입형+에셋형) — v5 패치를 modkit 어휘로
  재현하고 매니페스트 동봉, "v4 잔재 위 v5" 시나리오를 실제로
  진단→격리→설치. ② GameVault의 현대 Essentials 게임 하나로 묶음형 검증.
- **exe 스모크**: 윈도우 호스트에서 더블클릭→진단→얹기→빼기 한 바퀴.

## 범위 밖 (v1에서 하지 않는 것)

- pip 패키징·PyPI 공개(경로 임포트로 충분해질 때까지).
- 맥·리눅스 exe(코어는 크로스플랫폼이지만 배포 대상이 윈도우 유저).
- 모드 온라인 저장소·자동 업데이트.
- pokemon-z vendor 사본 교체(다음 배포 때 판단).
